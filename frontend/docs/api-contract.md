# API 연동 가이드

화면은 `Api`의 메서드와 화면용 데이터 타입을 사용한다. 서버 경로, 요청 필드, 응답 구조는 API 계층에서 변환한다. **이 문서의 기본 REST 경로는 프론트의 연결 설정이며, 백엔드의 확정 명세가 아니다.** 팀 API 명세에 맞춰 연결 설정을 변경한다.

연결 구조는 **프론트 → 백엔드 → AI 서버**다. 프론트는 백엔드에만 요청하며 AI 호출·저장·통계 계산은 백엔드와 AI 서버의 책임이다. Mock은 메모리에 저장하는 화면 검증용 구현으로, 실제 AI 분석이나 영구 저장을 제공하지 않는다.

## 수정 위치

| 변경 사항                            | 파일                                        |
| ------------------------------------ | ------------------------------------------- |
| 화면에 필요한 기능과 반환 타입       | `src/api/port.ts`, `types.ts`               |
| 연결할 계약·인증 헤더·지원 기능 선택 | `src/api/integration.ts`                    |
| 메서드별 HTTP 경로·쿼리·요청 본문    | `src/api/restContract.ts`의 `request`       |
| 서버 응답을 화면 데이터로 변환·검사  | 각 메서드의 `decode`, `src/api/decoders.ts` |
| AI 작업 상태와 완료 결과 해석        | 해당 메서드의 `job.read`                    |
| HTTP 전송·오류·전체 제한 시간        | `src/api/client.ts`, `httpApi.ts`           |
| 화면 개발용 데이터                   | `src/api/mock/`                             |

`features`와 `shared/report`에서는 `api`만 호출한다. 경로나 서버 DTO가 바뀌어도 해당 변경은 API 계층에서 처리한다. 화면에서 사용하는 정보 자체가 바뀔 때는 화면 타입과 UI도 수정한다.

## 연결 순서

1. 팀 API 명세에서 경로·입력·응답 예시·인증·오류·AI 처리 방식을 확인한다.
2. `.env.local`에서 주소와 쿠키 전송 방식을 설정한다.
3. `integration.ts`에서 계약을 선택하고 필요한 `request`, `decode`, `job`을 맞춘다.
4. 실제 응답 예시를 테스트에 추가한다. 미확인 필드를 임의 값으로 채워 성공 처리하지 않는다.
5. 서버와 연결해 메모 저장 → 정리 완료 → 확인·수정 → 재조회 → 요약지 흐름을 확인한다.

다른 경로·요청 필드·응답·영문 코드·비동기 작업을 사용하는 테스트 서버와의 연결 예시는 [server-contract.test.ts](../tests/server-contract.test.ts)에 있다. 이 테스트는 어댑터 동작을 검증하며 팀 서버의 연동 완료를 뜻하지 않는다.

## 주소와 인증

```dotenv
ITDA_API_TARGET=http://127.0.0.1:8000
VITE_API_BASE_URL=/api
VITE_API_CREDENTIALS=same-origin
VITE_USE_MOCK=false
```

- 개발 중 `/api/memos`는 Vite 프록시를 거쳐 `ITDA_API_TARGET/memos`로 전달된다. `/api` 접두어는 제거된다. 새 경로도 같은 접두어 아래에서 전달된다.
- `VITE_API_BASE_URL=https://api.example.com/v1`이면 브라우저가 해당 서버에 직접 요청한다. 개발 프록시는 사용하지 않는다.
- 기본 주소를 비워 두면 `config/devProxy.ts`의 루트 경로 목록만 프록시한다. 경로 확장이 필요하면 `/api` 설정을 사용한다.
- 배포 환경에는 Vite 개발 프록시가 없다. 웹 서버의 `/api` 역방향 프록시 또는 절대 API 주소를 설정한다.
- 쿠키 전송은 `same-origin`이 기본이다. 별도 origin의 쿠키 인증은 `include`와 서버 CORS 설정이 필요하다. `omit`도 선택할 수 있다.
- 토큰 인증은 `integration.ts`의 `httpOptions.headers`에 현재 세션 헤더를 반환하는 함수를 연결한다. 각 요청과 작업 조회 시 다시 읽는다. 세션 발급·갱신 방식은 인증 명세에 맞춰 연결해야 한다.
- `VITE_*` 값은 브라우저에 포함된다. API 비밀 키를 넣지 않는다. AI 모델 키도 프론트에 두지 않는다.

## 계약 선택과 변경

```ts
export const apiContract = createRestContract({
  enumStyle: 'codes', // 요청에 영문 코드 사용. 'labels'는 한글 값 사용
  envelope: 'bare', // { data: 결과 } 형태이면 'data'
  capabilities: { workspace: false, patient: true, demo: false },
})

// 경로와 입력 필드가 다른 경우 해당 메서드만 변경한다.
apiContract.endpoints.createMemo.request = (body) => ({
  path: '/v2/observations',
  method: 'POST',
  body: { content: body.text, observedOn: body.record_date, requestKey: body.request_id },
  timeoutMs: 260000,
})
```

`decode`는 서버 JSON을 받아 화면 타입을 반환한다. 예를 들어 서버가 `items`에 목록을 담으면 `items`를 검사한 뒤 `decoders.memos(items)`를 호출한다. 공통 `data` 감싸기와 각 메서드별 변환은 선택해서 사용한다. 날짜 필드명, UUID, 페이지 단위 목록 등 화면 타입과 의미가 다른 계약은 별도 매핑이나 화면 타입 변경이 필요하다.

요청 경로는 설정한 API 주소 아래의 `/`로 시작하는 경로만 사용한다. 서버가 반환한 임의 외부 URL에 인증 헤더를 보내지 않는다.

### 지원 기능

| 설정        | 의미                                          | 기본 |
| ----------- | --------------------------------------------- | ---- |
| `workspace` | 기록 공간 ID와 요청 헤더를 사용하는 서버 규약 | 끔   |
| `patient`   | 대상자 이름 조회·수정                         | 켬   |
| `demo`      | 서버의 별도 데모 기록 공간 전환               | 끔   |

지원하지 않는 이름 설정·데모 버튼은 숨기며 해당 API 호출도 차단한다. 대상자 이름 조회의 일반 오류는 기록 화면을 막지 않는다. 인증 오류와 기록 공간 변경은 입력을 보호하기 위해 차단한다.

기록 공간 규약을 켠 경우 `health`의 `workspace_id`를 채택한 뒤 `X-Itda-Workspace`를 전송한다. 작업 중 공간이 바뀌면 늦게 온 응답을 버린다. `demo`는 `workspace`와 함께 켜야 한다. 샘플 모드는 자체 메모리 공간 격리를 사용한다. 기록 공간 ID는 사용자 인증을 대신하지 않는다.

요청 인자와 화면 타입의 전체 필드는 [port.ts](../src/api/port.ts)와 [types.ts](../src/api/types.ts)를 참고한다. 삭제의 기본 성공 응답은 `204`이다. `envelope: 'data'`에서는 `200 { data: null }`도 읽는다. 그 밖의 삭제 응답은 해당 `decode`를 맞춘다.

메모 전체 삭제는 원문과 그 메모에 속한 사건·수정 이력을 함께 제거하는 동작이다. 확인 대기·정리 실패·확인 완료 메모를 모두 대상으로 한다. 삭제 성공 후 화면은 기록 목록과 경과·요약 데이터를 갱신하고, 실패하면 기존 기록을 유지한다. 같은 날짜의 다른 메모는 삭제하지 않는다. 연결할 서버에서는 삭제 범위·삭제 후 중복 저장 요청·진행 중인 AI 작업 처리도 이 동작에 맞게 확인한다. `/memos/{id}`는 변경 가능한 기본 매핑이다.

### 메모 원문 수정과 재정리

`updateMemo(id, { text, request_id? })`는 원문을 저장하고 다시 정리한 `MemoResult`를 반환한다. 메모 ID와 보호자가 선택한 `record_date`는 유지한다. 기본 `PATCH /memos/{id}`는 변경 가능한 프론트 매핑이며 팀 서버의 확정 경로가 아니다.

- 원문 변경을 저장할 때 이전 확정 상태·사건·모델 출력·사건 출처 번호를 함께 무효화한다. 새 결과는 `확인 대기`, 재정리 실패는 **저장된 새 원문**과 빈 사건을 포함한 `정리 실패`로 반환한다. 이전 사건을 새 원문의 결과로 재사용하지 않는다.
- 다시 확인하기 전에는 해당 메모를 경과·요약·근거·차트 집계에서 제외하고 관련 캐시를 갱신한다. 같은 날짜의 다른 확정 메모는 유지한다. 원문 저장 실패와 저장 후 AI 처리 실패를 구분해야 한다.
- 동일 `request_id`와 메모 ID·원문으로 재전송하면 저장·재정리를 중복 수행하지 않는다. 재전송 때문에 이후의 보호자 확정을 초기화해서도 안 된다. 같은 요청 번호의 다른 메모·원문, 이미 다른 원문으로 변경된 이전 요청, 삭제된 메모의 요청은 거부한다.
- 이전 원문을 처리하던 AI 작업이 늦게 완료되어 새 결과를 덮지 않도록 서버에서 원문 버전을 확인한다. 원문 변경과 이전 집계 무효화는 일관되게 처리해야 한다.
- 사건 수정 이력은 그 근거가 속한 원문 버전과 함께 관리한다. 샘플 API는 원문 수정 시 이전 `memoRevisions`를 초기화하고 새 원문에 대한 확인 이력을 시작한다. 서버에서 과거 이력을 보관한다면 현재 원문의 수정 이력과 구분해 반환한다.

수동 사건 추가의 `evidence`는 보호자가 원문에서 선택한 구절이며 비어 있거나 원문에 없는 문자열이면 안 된다. 전체 메모를 임의로 근거로 채우지 않는다. 수동 사건은 `model_event_index: null`을 사용한다. 유형·횟수·시간 표현을 수정해도 선택한 근거 구절은 유지한다.

기존 카드의 근거도 원문에서 다시 선택할 수 있다. 카드 수정은 `evidence`를 바꾸되 기존 `model_event_index`를 유지하며, `수정 적용`은 편집 중인 카드에만 반영한다. `확인 완료` 또는 `다시 확정`에서 사건 전체를 저장한다. 근거 선택은 원문 텍스트 자체를 변경하지 않는다.

확인 화면은 발생한 사건만 카드로 편집한다. 잘못 추출한 사건은 카드를 삭제하며, `있었음/없었음`을 고르는 입력은 제공하지 않는다. `confirmMemo.events`는 최종 사건 목록 전체를 뜻하므로 빠진 카드를 서버가 유지하거나 추가 방식으로 합치면 안 된다. `absent/없었음`은 응답 호환을 위해 타입·디코더에서 읽지만 사용자에게 별도 상태 선택을 요구하지 않는다. 사건이 없는 메모도 빈 목록으로 확인 완료할 수 있다.

## 응답 검사와 코드 변환

- `unknown` 응답을 검사한 뒤 화면에 전달한다. 필수 필드·잘못된 날짜·숫자·알 수 없는 상태를 조용히 통과시키지 않는다.
- 기본 사건 유형은 `night_waking` 등 12개 영문 코드와 한글 값을 모두 읽는다. 상태 `present/absent`, 메모 `pending/confirmed/failed`, 약 변경 `start/increase/decrease/stop`도 화면 라벨로 변환한다. 요청은 선택한 `enumStyle`에 맞춘다.
- 기본 화면 비율은 `0~1`, 날짜는 `YYYY-MM-DD`, ID는 양의 정수이다. 서버가 `36%`를 `36`으로 보내면 어댑터에서 `0.36`으로 변환한다. 계산 기준 자체를 프론트에서 바꾸지는 않는다.
- `{ events: [...] }` 형태의 AI 원시 결과만으로는 저장된 메모가 되지 않는다. 메모 ID·원문·기준 날짜·처리 상태·검증된 사건을 포함하는 응답과 연결한다. AI는 사건별 날짜를 만들지 않는다. 메모의 `record_date`를 모든 사건에 공통으로 적용한다.
- `health`는 최소 `{ ok: true }`를 읽는다. AI 준비 상태가 없으면 `null`로 유지하며 준비 완료나 연결 실패로 단정하지 않는다. 응급 키워드 등 추가 정보가 없는 경우 해당 기능이 제공된 것으로 간주하지 않는다.

`config/labels.json`은 동결된 팀 설정이다. API 코드 변환은 `decoders.ts`에서 관리하며, 팀 코드 확정 시 매핑과 테스트를 함께 맞춘다.

## 기록 날짜와 집계 기준

`MemoResult.record_date`는 보호자가 메모 입력 시 선택한 날짜다. 실제 저장 시각이 아니다. 메모 한 건에는 선택한 날의 일만 담으며, 모든 사건은 메모의 날짜를 공유한다.

```json
{
  "text": "새벽 3시쯤 깨서 현관문 열려고 하심.",
  "record_date": "2026-09-23",
  "request_id": "중복 요청 확인용 ID"
}
```

- 9월 28일에 화면을 열어 9월 23일을 선택해 저장하면, 해당 메모와 사건은 모두 **9월 23일** 기록이다.
- AI는 유형·상태·시간 표현·횟수·근거를 추출한다. `time_expr`가 있어도 날짜를 더하거나 빼지 않는다. 사건 확인·수정과 직접 추가에서도 별도 날짜를 입력하지 않는다.
- `EventCard`에는 사건별 날짜와 날짜 미정 필드를 두지 않는다. 메모 조회·기간 검색·주간 추이·요약지·근거 날짜는 모두 `record_date`를 사용한다.
- 통계 분모는 기간 안의 **확인 완료 메모가 있는 서로 다른 날짜 수**다. 사건 없는 메모도 확인 완료하면 포함한다. 같은 날짜에 메모가 여러 건이어도 하루로 센다.
- 유형별 발생일 수는 해당 유형을 ‘있었음’으로 확인한 **서로 다른 기록 날짜 수**다. 같은 날 여러 번 관찰한 횟수는 별도로 합산한다.
- 확인 대기·정리 실패 메모는 통계에서 제외한다. 날짜는 필수로 선택하므로 날짜 미정 제외 항목은 없다.
- 서버의 `created_at` 등 저장·수정 시각은 운영 이력용으로 분리하며 통계 날짜에 합치지 않는다.

실제 통계 계산은 백엔드가 이 기준으로 수행하고, 프론트는 계산된 요약·추이를 표시한다. 샘플 API도 같은 날짜 기준으로 집계한다. 서버 필드명이 다르면 어댑터에서 `record_date`로 연결한다.

## 진료 준비와 요약 기간

| 데이터  | 날짜와 기능 기준                                                                             |
| ------- | -------------------------------------------------------------------------------------------- |
| 진료일  | 받은 진료는 `완료`, 다음 예약은 `예정`으로 등록한다. 날짜와 상태를 함께 저장한다.            |
| 약 변경 | `change_date`에 발생한 변경 이력이다. 약 때문에 관찰 내용이 바뀌었다고 판단하지 않는다.      |
| 질문    | `created_at`의 날짜가 요약 시작일·종료일 사이에 있으면 포함한다. 양 끝 날짜를 모두 포함한다. |

질문은 기록·일정 화면 모두 `addQuestion({ text })`로 저장한다. 현재 `period_start`, `period_end`는 선택적 계약 필드이며 화면에서 지정하지 않고, 질문 포함 여부를 바꾸는 선택 기능도 없다. `questionInPeriod()`는 `created_at.slice(0, 10)`을 사용하므로 서버 시각의 날짜가 서비스 기준 날짜와 같도록 시간대 표현을 맞춘다. 서버의 `Summary.questions`도 이 규칙과 일치해야 한다.

경과·요약지·일정의 요약 기간은 `as_of`, `period_start`를 공유한다. 기본 종료일은 오늘이며 시작일을 지정하지 않으면 서버의 기본 기간을 사용한다. Mock은 최근 완료 진료일 → 최초 확정 기록일 → 종료일 순으로 시작일을 정한다. 비교 기간은 해당 시작일 이전의 완료 진료일부터 시작일 전날까지이며 이전 진료가 없으면 `null`이다. 실제 서버의 기본·비교 기간 정책을 확인하고 반환된 `period`, `baseline`을 연결한다. 프론트가 서버 집계의 기간을 임의로 바꾸지 않는다.

경과·요약지·PDF에서 약 변경과 낙상은 각각 별도 영역으로 표시한다. API는 기존의 `Summary.medications`와 `Summary.falls`를 독립 필드로 유지하며, 화면을 나누기 위해 새 엔드포인트나 혼합 이벤트 형식을 추가하지 않는다.

## 저장 후 갱신과 출력 흐름

- 저장·확정·삭제 성공은 반환값을 화면에 반영하고 `itda-final-updated`로 기록·질문 목록과 보고서 데이터를 갱신한다. 서버는 성공 응답 뒤 재조회에서 최신 값을 반환해야 한다. 최종 상태가 늦게 반영되는 서버라면 작업 완료 규약과 재조회 시점을 함께 맞춘다.
- 기록 화면은 질문 저장 응답을 최근 질문 목록에 즉시 반영한 뒤 재조회한다. 최근 질문은 기본으로 접혀 있고 저장 성공 시 펼친다. 목록에는 최근 3건을 표시하며 전체 관리는 일정에서 한다.
- 정리된 내용은 팝업으로 열며, 닫은 뒤 최근 기록·지난 기록에서 다시 열 수 있다. 지난 기록에서 연 메모는 닫기·확정·삭제 후 같은 목록으로 돌아간다.
- PDF 출력 전 확인 목록에서 개별 메모를 열었다면 닫기·확정·삭제 후 **출력 전 기록 확인 팝업**으로 돌아간다. 삭제·확정 결과를 재조회해 남은 기록 수를 갱신하고 선택 기간은 유지한다. 모두 처리해도 자동 인쇄하지 않는다.
- PDF는 브라우저 인쇄 기능으로 저장한다. 현재 `Api`에는 PDF 생성·다운로드 메서드가 없다.

`useSummary`는 같은 훅이 유지되는 동안 기간·AI 옵션·데이터 변경 상태별 요청과 결과를 메모리에 재사용한다. 변경 알림을 받으면 무효화하며 새로고침 이후까지 보관하지 않는다. 서버도 같은 대상자·기간·데이터 버전의 요약 재사용과 데이터 변경 시 무효화 정책을 제공해야 불필요한 AI 재생성을 막을 수 있다.

## AI 처리 방식

화면의 `api.createMemo()`, `updateMemo()`, `retryMemo()`, `summary()`는 완성된 화면 데이터를 반환하는 Promise다. 백엔드와 AI 사이의 실행 방식은 화면 컴포넌트에 넣지 않는다.

- **즉시 응답:** 결과 JSON을 `decode`로 검증해 반환한다.
- **작업 조회:** 해당 메서드의 `job.read`를 설정한다. 각 응답을 `pending`(다음 조회 요청·대기 시간), `complete`(완료 값), `failed`(오류 메시지·코드) 중 하나로 해석한다. 완료 값은 다시 `decode`로 검사한다.
- 작업의 `pending`은 분석 중을 뜻하고, 메모 응답의 `pending`은 분석 후 보호자의 확인 대기를 뜻한다. 두 상태를 같은 것으로 매핑하지 않는다.
- `202`만 받고 작업 규약이 설정되지 않았으면 연동 오류로 처리한다. 이를 정리 완료로 표시하지 않는다.
- 메모 작성·원문 수정 요청은 자동 재전송하지 않는다. 작업 조회는 같은 작업을 확인하는 GET 요청이다. `request_id`의 중복 방지는 서버와 합의해 구현한다.
- 작업 생성, 인증 헤더 조회, 응답 수신, 조회 대기 전체가 하나의 제한 시간을 사용한다. 기본 일반 요청 15초, 메모 정리 260초, AI 요약 375초다. 제한 시간 초과가 서버 작업 취소를 의미하지는 않는다.
- 스트리밍·SSE와 작업 취소 API는 아직 제공하지 않는다. 해당 방식으로 합의하면 API 계층에 추가한다.

## 오류와 검증

`ApiError`는 HTTP 상태와 오류 코드를 보존한다. HTML 오류 응답을 네트워크 단절로 바꾸지 않는다. 잘못된 성공 JSON은 `invalid_response`, 미설정 비동기 방식은 `unsupported_async`로 구분한다. 서버 오류 문구는 기본적으로 `detail` 또는 `message`를 읽으며 다른 오류 구조는 전송 옵션의 오류 변환 함수로 연결한다. 실제 요청 실패를 샘플 데이터로 대체하지 않는다.

자동 검증에는 다른 계약의 테스트 서버 연결, 요청·응답 변환, AI 작업 성공·실패·시간 초과, 응답 오류, 기록 공간 변경, 선택 기능 없이 앱 시작, 샘플 화면 흐름이 포함된다. 실제 팀 서버에서는 인증·재접속·중복 저장·AI 실패·요약·출력을 별도로 확인한다.
